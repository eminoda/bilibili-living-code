# Vite 8 订单运营工作台

本项目是《Vue3 + Vite 8：启动 0.1 秒，首屏加载怎么还白屏？》的可录屏 Demo。界面是一套零售运营后台，覆盖订单、履约、库存、客户、财务和经营分析六个业务域，共 72 个可导航业务页，由六类领域工作台承载。首页 KPI、回款趋势、渠道占比和订单表格共享同一份订单样本；点击渠道会联动筛选订单，趋势和渠道图由 ECharts 绘制。界面统一使用 Element Plus，ECharts 负责趋势与渠道图；固定本地业务样本不依赖后端请求。

## 运行

依赖已安装后，Live Coding 只需激活这个 Vite 8 项目，并在该项目目录执行：

```powershell
cd apps/living-projects/vite8-order-workbench
npm run dev
```

首次准备工作区依赖时，在仓库根目录执行一次 `pnpm install`。录制时不需要运行其他项目；切换 `bundledDev` 后，仍在这个目录重启 `npm run dev`。

若终端停在仓库根目录，可执行 `npm run dev:vite8`，只启动本项目。根目录的 `npm run dev` 会同时启动工作区里其他项目，不适合本期 Live Coding。端口 5178 被旧实例占用时，先停止该实例再启动；不要同时运行两份订单项目。

访问 `http://127.0.0.1:5178/orders`。点击侧栏业务模块，可以进入对应页面；首页的筛选、分页、订单详情、任务入口、导出和新建订单均可操作。

项目需要 Node 22.18+ 或 24.12+。当前固定 Vite 8.3.2；依赖版本见 `package.json`。

## 为什么会发出真实的模块请求

`src/router.ts` 使用同步路由注册：`import.meta.glob(..., { eager: true })`。每个业务页通过模块定义、权限和记录进入六个业务域；每个域另有自己的流程样本和处理逻辑。订单审核、履约时效、可售库存、客户工单、平台对账和渠道转化使用不同的数据模型，不再共用同一张模板数据。首页以 `useOrderFilters.ts` 维护订单状态，`useDashboardAnalytics.ts` 派生 KPI、日期回款与渠道指标；渠道选择会向订单筛选状态发出动作。ECharts 仅注册当前实际使用的柱状图、折线图、环形图、坐标轴与提示框模块。首页运营侧栏和图表也消费跨域汇总结果，所以这些模块进入 `/orders` 的真实首屏依赖图。

首页图表口径是**固定本地业务样本的可重复计算**，不是线上实时经营数据。这里不调用真实 API：接口等待会把 Lighthouse 结果混入后端延迟，且 `bundledDev` 不会让接口响应更快。需要评估接口体验时，应另做网络链路实验，不能和本期模块交付对比混为一谈。

首页使用 Element Plus 与按需注册的 ECharts 图表；这些真实依赖会增加两种模式共同承担的脚本与渲染工作，不能被解读为 `bundledDev` 的预期收益。正式记录要在依赖安装、浏览器预热完成后，基于同一 URL 和缓存协议重测，比较首页 Ready、FCP/LCP、请求数和 Lighthouse 分数。

业务域按常见的纵向切片组织：`workflow.ts` 保存领域样本与可推导指标，`*Workbench.vue` 组合域流程和通用列表，`DomainSnapshotPanel.vue` 复用信息展示，`operationsSnapshot.ts` 聚合首页待办。72 个路由是六个业务域下的导航业务页，不代表 72 套独立流程实现；模块图的业务复杂度来自领域规则、跨域汇总与首屏同步注册，不靠空文件、随机导入或人为等待。

这是一种**特定项目架构**：集中注册全部管理后台路由，并在启动时 eager 加载路由组件。许多现代项目会按路由懒加载；那会缩小 `/orders` 的首屏模块图，也会减小本实验中 bundledDev 可影响的范围。此处保留同步注册，是为了测试一个常见的历史后台组织方式，不代表所有 Vite 项目都应该这样写。路由清单由 `scripts/generate-business-modules.mjs` 生成。

## 录制两种模式

`vite.config.ts` 当前为 `experimental.bundledDev: false`。录制默认模式后，将这一项改为 `true`，**重启**开发服务器，再录制同一路由。该选项属于 Vite 8.1 起的实验性功能，须核对插件兼容性。

### 固定缓存与页面 Ready 口径

两种模式都按同一协议录制。Vite 会把预构建依赖缓存在 `node_modules/.vite`，浏览器也会强缓存依赖请求；因此每轮都要保留缓存状态记录，不能一边勾选 Chrome Network 的 **Disable cache**、另一边不勾。[Vite 依赖预构建与缓存说明](https://vite.dev/guide/dep-pre-bundling.html)

本次扩展业务域后，之前 72 个轻量模板页版本的测量只能作为旧版记录；必须在同一新版源码上重新采集默认模式和 bundledDev 模式，不能把新旧页面的数据拼成 Before / After。

1. 固定同一机器、Chrome 版本和 **1920×1080** 视口，不改代码、路由、数据和插件。每种模式先用当前配置启动一次、打开 `/orders` 让依赖预构建完成，然后停止服务；这次预热不计入结果。不要清理 `node_modules/.vite`，也不要加 `--force`。
2. 用相同配置重新执行 `npm run dev`，保留新的终端 `ready` 原始输出。每次正式首访都打开一个**全新的无痕窗口或非持久化浏览器上下文**，保证浏览器缓存起点为空；DevTools 的 **Disable cache 保持关闭**。从导航到 `http://127.0.0.1:5178/orders` 开始录制。
3. **业务主内容 Ready** 固定定义为：订单统计卡与订单表格第一行**同时在视口内可见**。页面根节点 `data-testid="orders-main"` 只是定位范围；采集脚本还会等待 `orders-stats` 中的统计卡和 `orders-table` 中的首行，并读取随后一帧的 `orders-main-ready` 辅助标记。FCP 或只有页面标题出现均不算业务 Ready。
4. 首访完成后，**保持同一服务器、同一窗口与缓存设置**，在同一 `/orders` 页面按 **Ctrl+R 普通刷新**，再录到同一个 Ready 条件。不要用强制刷新。Network 的同源 JS 请求数按“开始导航或刷新 → Network 空闲”的同一窗口统计；它与主内容 Ready 时间是两个独立指标。
5. 每种模式至少录 **3 轮**，保留每轮原始数据并以中位数作结果卡；两边都按上述预热、首访和刷新顺序执行。若出现重新预构建、请求失败或页面自动二次加载，保留日志并单独注明，不把异常轮次混进正常结果。脚本的 `mainFrameNavigations` 大于 1 时，应检查是否发生自动二次加载。

正式视频只需一句口径说明：“两边都用同样的浏览器缓存规则；首访从空浏览器缓存开始，刷新则沿用同一页面的缓存。”`ready` 和浏览器的 Ready 是不同起点，不相减算“白屏时长”。

两组都保存终端 `ready` 输出、首访和刷新的完整录屏、对应的 Chrome Performance 与 Network Waterfall，以及缓存状态和失败请求。

S02 只剪出 **1–2 个最有画面冲击的已测结果**作为预告；若只有请求数变化而页面时间收益有限，照实说。S03 再用 **首访 Before / After → 全量刷新 Before / After → 同一张四行结果卡** 完整证明，约 50 秒。下一段立刻回看这一轮实验的 Network，不另造与结果卡不对应的抓包。

## 录制“日常改代码的反馈链路还在吗？”

订单页的“支付状态”由 `src/features/dashboard/components/OrderStatus.vue` 独立渲染，默认有可见的“已支付”标签；这是实际订单字段，不是专为热更新导入的空组件。

1. 在默认模式打开 `/orders`，在订单搜索框输入 `BC202609`，让筛选条件和“已支付”标签同屏。保留浏览器导航记录。
2. 编辑 `OrderStatus.vue` 的模板，只把 `<template v-if="status === '已支付'">已支付</template>` 中的可见文案改为“支付成功”并保存；判断条件保持不变。录下页面标签变化、是否发生全量导航，以及搜索词是否保留。
3. 第一轮镜头结束后先停止开发服务器，恢复原文并切换 `bundledDev: true`；仍在本项目目录执行 `npm run dev`，用相同路由、筛选词和编辑动作录第二轮。

在当前固定的 Vite 8.3.2 下，已做过一次本机冒烟检查：实验模式保存上述模板文案后，页面标签更新、订单筛选词 `BC202609` 保留，且没有整页导航。正式镜头仍须按同一动作原始录制。此前 Vite 8.3.1 下同一改动出现 `factory.fn is not a function`，所以本项目固定到 8.3.2；这不代表所有插件组合都已兼容。

此镜头验证**本项目这一组件改动是否被热更新**，不是 HMR 速度基准；单次录屏不支持“比 webpack 快”的结论，webpack 本身也支持 HMR。若正式录制时实验性模式发生全量刷新或插件异常，保留原始结果并修正视频结论。正式判断还要结合首访、全量刷新与插件功能，Server CPU/I/O 本期未测时不作推断。

`node scripts/capture-demo.mjs default` 会在新浏览器上下文中留下首次访问、普通刷新、固定 Ready 条件与请求清单的单次记录（输出到被忽略的 `captures/`）。切换配置并按上述协议重新启动后，用 `node scripts/capture-demo.mjs bundled` 采集另一组。两份**新口径** JSON 都有后，运行 `node scripts/compare-demo.mjs default bundled`，会生成明确标为草稿的 `captures/comparison-draft.md`。草稿的 `ready` 与页面时间仍留空，正式结论需同步录屏和多次测量；脚本中的 `orders-main-ready` 是满足两处可见条件后的辅助时间点，还需与画面帧核对。

目前已确认：两种配置都能渲染同一业务页面，默认模式确实产生数百个源码模块请求，实验模式的该次本机检查只有少量请求。**“0.1 秒 ready”、数秒白屏或稳定的页面提速幅度仍未证明**。录制若不能稳定支持标题，就按已确认的 outline 调整标题与叙事结论，不能用剪辑制造差异。
